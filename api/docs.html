Availability

The Risk API and Prop Firm Rules API are in development. Key issuance, a developer dashboard, sandbox execution and billing will arrive in later build stages. The public pages do not claim these services are live.

Forex is the initial Risk focus. Broker-specific symbol specifications are still being verified. Liquidation and options endpoints are deferred.

Your first request

  1. Request launch access through Get API Key. Keys are not issued yet.
  2. When available, create a test key in the developer dashboard.
  3. Store the key in a server environment variable named FYNX_API_KEY.
  4. Send decimal inputs as strings and inspect the result and warnings.

This example assumes EURUSD, 100,000 units per lot and a 0.01-lot step. The final schema must include or resolve verified instrument metadata.

curl · draft
curl -X POST "https://api.fynxfinanceworld.com/v1/risk/position-size" \
  -H "Authorization: Bearer $FYNX_API_KEY" \
  -H "Content-Type: application/json" \
  --data '{"account_balance": "10000.00", "risk_percent": "1.0", "entry_price": "1.0850", "stop_loss_price": "1.0820", "symbol": "EURUSD", "instrument_type": "forex", "account_currency": "USD", "direction": "long"}'

Authentication

Planned header: Authorization: Bearer <API_KEY>. Test and live environments will have separate keys. Keys will belong to an organization, so rotating a key will not remove its accounts or rule sets.

Keep private keys on your server. Browser and mobile apps should call your backend rather than embed an unlimited FYNX secret.

Risk endpoint reference

All planned Risk routes use POST with a JSON body. This is a contract summary, not a finalized OpenAPI schema.

POST /v1/risk/position-size

Inputs: Budget, entry, stop, direction, instrument metadata, account currency and conversion basis.

Returns: Floored quantity and actual modeled risk.

POST /v1/risk/risk-reward

Inputs: Entry, stop, take-profit, direction; optional estimated win rate.

Returns: R:R, break-even win rate, optional expectancy in R.

POST /v1/risk/pip-value

Inputs: Symbol metadata, lot size, account currency and conversion rate.

Returns: Pip value in account currency.

POST /v1/risk/margin

Inputs: Lots, contract size, entry, leverage and currency conversion.

Returns: Notional value and simple required margin.

POST /v1/risk/break-even

Inputs: Entry basis, direction, spread, commission currency and round-trip commission.

Returns: Modeled break-even price.

POST /v1/risk/atr-stop

Inputs: ATR value, multiplier, entry and direction.

Returns: Theoretical stop price.

Prop firm endpoint reference

Method / routePurpose
POST /v1/propfirm/rule-setsCreate an immutable version of explicit numerical rules.
POST /v1/propfirm/accountsCreate a phase account pinned to a rule version.
POST /v1/propfirm/accounts/{id}/eventsApply an ordered, idempotent account event.
GET /v1/propfirm/accounts/{id}/statusRead balances, rule metrics, eligibility and source-data health.
GET /v1/propfirm/accounts/{id}/eventsRead paginated event and evaluation history.

Event example

A close includes the total remaining unrealized P&L after that close. Replacing the unrealized snapshot prevents double counting the same loss.

POST account event · proposed schema
{
  "idempotency_key": "close-001",
  "source_event_id": "provider-close-001",
  "sequence": 1,
  "event_type": "closed_trade",
  "realized_pnl": "-150.00",
  "unrealized_pnl_after": "0.00",
  "open_position_count": 0,
  "timestamp": "2026-09-21T14:32:00Z",
  "symbol": "EURUSD"
}

Realized P&L must be net of applicable costs. Duplicate keys with an identical payload return the original result; changed payloads or new out-of-order events produce a conflict. Final field names will be frozen before v1 access.

Limits and assumptions

Calculation outputs depend on your inputs. There is no live pricing, trade execution or investment advice. Modeled stop losses exclude unmodeled execution costs and cannot guarantee fills.

Prop evaluations reflect accepted source events. Missing observations, stale marks or absent daily-boundary data must be surfaced before a definitive completion decision.

Rate limits, usage allowance and paid terms are described on the pricing preview. OpenAPI downloads and interactive requests will be published with the actual service.
