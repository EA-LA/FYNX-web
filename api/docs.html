Your first request

  1. Create an account through Get API Key. Verify your email before creating keys.
  2. Create a test key in the developer dashboard.
  3. Store the key in a server environment variable named FYNX_API_KEY.
  4. Send decimal inputs as strings and inspect the result and warnings.

This example assumes EURUSD, 100,000 units per lot and a 0.01-lot step. Send contract_size, quote_to_account_rate, lot_step and minimum_lot explicitly. These values are caller supplied, not broker verified.

curl · beta
curl -X POST "https://us-central1-fynx-c7a28.cloudfunctions.net/developerGateway/v1/risk/position-size" \
  -H "Authorization: Bearer $FYNX_API_KEY" \
  -H "Content-Type: application/json" \
  --data '{"account_balance": "10000.00", "risk_percent": "1.0", "entry_price": "1.0850", "stop_loss_price": "1.0820", "symbol": "EURUSD", "instrument_type": "forex", "contract_size": "100000", "quote_to_account_rate": "1", "lot_step": "0.01", "minimum_lot": "0.01", "account_currency": "USD", "direction": "long"}'

Authentication

Authentication header: Authorization: Bearer <API_KEY>. Test and live environments have separate keys. Keys belong to your workspace, so rotation does not remove accounts or rule sets.

Keep private keys on your server. Browser and mobile apps should call your backend rather than embed an unlimited FYNX secret.

Risk endpoint reference

All Risk routes use POST with a JSON body. This is a contract summary, not a finalized OpenAPI schema.

POST /v1/risk/position-size

Inputs: Budget, entry, stop, direction, instrument metadata, account currency and conversion basis.

Returns: Floored quantity and actual modeled risk.

POST /v1/risk/risk-reward

Inputs: Entry, stop, take-profit, direction; optional estimated win rate.

Returns: R:R, break-even win rate, optional expectancy in R.

POST /v1/risk/pip-value

Inputs: Symbol metadata, lot size, account currency and conversion rate.

Returns: Pip value in account currency.

POST /v1/risk/margin

Inputs: Lots, contract size, entry, leverage and currency conversion.

Returns: Notional value and simple required margin.

POST /v1/risk/break-even

Inputs: Entry basis, direction, spread, commission currency and round-trip commission.

Returns: Modeled break-even price.

POST /v1/risk/atr-stop

Inputs: ATR value, multiplier, entry and direction.

Returns: Theoretical stop price.

Prop firm endpoint reference

POST /v1/propfirm/rule-setsCreate an immutable version of explicit numerical rules.
POST /v1/propfirm/accountsCreate a phase account pinned to a rule version.
POST /v1/propfirm/accounts/{id}/eventsApply an ordered, idempotent account event.
GET /v1/propfirm/accounts/{id}/statusRead balances, rule metrics, eligibility and source-data health.

Event example

A close includes the total remaining unrealized P&L after that close. Replacing the unrealized snapshot prevents double counting the same loss.

POST account event · beta schema
{
  "idempotency_key": "close-001",
  "source_event_id": "provider-close-001",
  "sequence": 1,
  "event_type": "closed_trade",
  "realized_pnl": "-150.00",
  "unrealized_pnl_after": "0.00",
  "open_position_count": 0,
  "timestamp": "2026-09-21T14:32:00Z",
  "symbol": "EURUSD"
}

Realized P&L must be net of applicable costs. Duplicate keys with an identical payload return the original result; changed payloads or new out-of-order events produce a conflict. For the current beta, an account event uses the field names shown above. Equity marks omit realized_pnl; all events require the next sequence number and current open-position count.

Event ordering and overnight positions

Submit each event with the next sequence number, a unique source_event_id and an idempotency_key. A retry with the same fields returns the original result without using another monthly call; JSON field order does not matter. Changing the payload under the same key is rejected.

When a position remains open across the daily reset, first submit a boundary_snapshot exactly at the next reset instant. Set unrealized_pnl_after to the source equity mark at that instant and preserve open_position_count. The snapshot carries balance forward and checks the prior daily loss limit before resetting. Submit one snapshot for every crossed reset; do not estimate missing source values.

{
  "idempotency_key": "boundary-20260921",
  "source_event_id": "provider-boundary-20260921",
  "sequence": 2,
  "event_type": "boundary_snapshot",
  "timestamp": "2026-09-21T22:00:00Z",
  "unrealized_pnl_after": "-200.00",
  "open_position_count": 1
}

Accepted events contain engine_version, payloadHash and chained event hashes for integrity checks. These records reflect submitted data; they do not establish broker completeness or payout approval. Corrections require a separately reviewed recovery process.

Successful calls use the monthly allowance. Failed calls and event replays do not, but authenticated attempts still use the per-second rate limit. Your lower saved request cap is enforced atomically across all keys.

Run the integration check

For account rules, download the Prop Firm Rules Node quickstart and run node prop-firm-quickstart.mjs with your test key. It creates one clearly named synthetic rule set and account, checks two ordered events, an identical retry, a conflicting retry, status and linked audit records.

This check uses six successful test calls and retains its test records. Run it in a quiet test workspace so the usage comparison is meaningful. Do not blindly retry account or rule creation after a timeout; inspect the workspace for the printed run name first. Internal script success does not count as an external beta result.

Use Node.js 22 or newer and a test key from your developer workspace. Download the Node quickstart, set FYNX_API_KEY in your local environment, and run node quickstart.mjs. Keep the key out of source files and browser code.

The script verifies a 0.33 lot result and the expected validation error for an invalid stop. It consumes one successful test call. The example contract values are illustrative. If you get stuck, submit a support ticket with the request ID and your runtime; never include your key.

Limits and assumptions

Need help? Use Settings & support in your workspace. Include the request ID and expected result, never your API key. No support response-time or uptime SLA is offered in this beta.

Calculation outputs depend on your inputs. There is no live pricing, trade execution or investment advice. Modeled stop losses exclude unmodeled execution costs and cannot guarantee fills.

Prop evaluations reflect accepted source events. Missing observations, stale marks or absent daily-boundary data must be surfaced before a definitive completion decision.

Rate limits, usage allowance and paid activation status are described on the pricing page. Try actual requests in the developer workspace. OpenAPI downloads remain future work.
